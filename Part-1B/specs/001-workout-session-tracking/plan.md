# Implementation Plan: Workout Session Tracking

**Branch**: `001-workout-session-tracking` | **Date**: 2026-11-23 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification and user-selected stack: React with Vite, Node.js with Express, SQLite, Zod, REST JSON API, configurable external LLM, and parser evaluation harness.

## Summary

Build a local-only, single-user workout tracker. A React/Vite interface communicates with an Express API bound to loopback; the API persists sessions, catalog exercises, and sets in SQLite. Manual and natural-language flows use the same domain validation and workout services. The backend sends workout text to the user's configured LLM provider/model, validates structured JSON and catalog/domain invariants, and only then calls persistence logic. Each installation owns one history with no authentication or account switching. The predefined catalog is seeded and not user-editable in this MVP.

## Technical Context

**Language/Version**: JavaScript ES modules; supported Node.js LTS at implementation time

**Primary Dependencies**: React, Vite, Express, Zod, better-sqlite3 behind a repository boundary, backend fetch adapters for OpenAI and Gemini structured-JSON APIs, Vitest coverage, Supertest HTTP integration client

**Storage**: File-backed SQLite owned by the backend; versioned migrations and idempotent catalog seed; foreign keys enabled for every connection; transactional writes for sessions and nested exercises/sets

**Testing**: Unit and integration tests; at least 85% statement and branch coverage across backend services/validators and critical frontend workout reducers. Parser dataset evaluation has a separate 80% all-layer case-pass target.

**Target Platform**: One-device local browser and Node.js server. Express and Vite bind only to loopback (`127.0.0.1`); API calls from other devices are not accepted. The backend may make outbound HTTPS requests to the selected external LLM.

**Project Type**: Web application (frontend + backend)

**Performance Goals**: Logging a set during an active workout takes under five seconds in usability acceptance checks. No throughput target is needed for the individual-user MVP.

**Constraints**: React frontend; Node.js/Express backend; SQLite persistence. All app listeners are loopback-only. Capture the browser's local date/time and IANA time zone for session creation and parsing. LLM credentials and provider calls stay in the backend; provider output is structured JSON, schema-validated, then checked against catalog and workout rules before persistence. Weight and repetitions must both be greater than zero. No user identity column or authentication layer is needed. Every API response is JSON; validation errors use 400, missing sessions use 404, and unexpected errors are sanitized 500 responses.

**Scale/Scope**: One local user per installation; any number of sessions, session exercises, and sets; fixed seeded exercise catalog; Pending and Completed lifecycle. Authentication, multi-user ownership, catalog management, remote access, and unit conversion are out of scope.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

- **Modular architecture**: PASS. Keep React views/components/state, Express routing, request schemas, domain services, SQLite repositories, and LLM integration in separate modules.
- **Focused logging flow**: PASS. The MVP centers on sessions, catalog exercises, and variable sets; the manual set-entry acceptance target remains under five seconds.
- **Safe natural-language interpretation**: PASS. The LLM runs behind a backend adapter, returns structured JSON, has no persistence access, and cannot bypass Zod plus deterministic catalog and value checks.
- **REST and reusable UI**: PASS. Document resource-oriented JSON endpoints and reusable React components/state management.
- **Validation, errors, and critical tests**: PASS. Validate at API and domain boundaries; test invariants and critical reducers; configure the requested coverage threshold.
- **Security and local boundary**: PASS. Bind frontend and API listeners to loopback. Keep the user's LLM key in backend-only runtime configuration and out of source, client bundles, logs, and responses. Allow only the backend's outbound provider calls.
- **Simplicity**: PASS. One frontend, one backend, one SQLite database, and one LLM adapter; no authentication, database server, or queue.

No constitution violations require an exception.
